# 双人共记 · 首条流程规格

目标：甲记下一笔午饭支出，乙接受邀请后，在自己的设备上读到相同的流水；乙切回个人账本时，两本账的数据各自独立。范围与成员权限以[一期 PRD](../product/微信小程序一期PRD.md)为准。

本条覆盖[功能总表](../product/产品功能总表.md)中的 AUTH-01～03、TX-01、BOOK-01、BOOK-03～06，以及 BOOK-08 的跨端读取。下一条再覆盖乙记第二笔、双方并发编辑和小簿文字对话确认。本条包含首次保存结果不明时的提示，不自动重发。

## 用户流程

测试使用首次进入的甲、乙两个独立身份。甲的个人账本为空；乙可以已有自己的账本。双方选择覆盖记账日期的同一查询范围。

| 步骤 | 用户操作 | 可观察的结果 |
| --- | --- | --- |
| 1 | 甲浏览示例，点「记一笔」，取消登录后再点一次并登录 | 取消时仍可浏览示例；登录成功后回到记账表单，目标为甲的个人账本。示例流水未带入 |
| 2 | 甲选择支出、餐饮，填 32 元，日期选今天，备注午饭，保存 | 流水页出现一笔午饭，支出合计 32 元。详情显示记账人「我」。退出后以同一身份重进仍能找到该笔 |
| 3 | 甲从「成员与邀请」选「可记账」，点「邀请微信好友」分享给乙 | 乙打开卡片能查看账本名、邀请人及拟授予的角色；接受前只能看到邀请摘要。甲取消分享也不会给乙授予成员权限 |
| 4 | 乙从卡片登录并确认加入 | 登录后接回同一邀请，成功后进入被邀请的账本。甲刷新成员列表看到乙，乙的角色为「可记账」 |
| 5 | 乙打开午饭流水，再切回自己的个人账本 | 共享账本中显示一笔 32 元的餐饮支出，日期、备注与甲一致，记账人显示甲的可辨认名称。乙个人账本中没有甲的这笔午饭 |

## 边界验收

| 用例 | 操作与预期 |
| --- | --- |
| 提交在途和结果不明 | 甲双击保存时界面不重复发请求。首次写入后返回途中断网，恢复后提示先刷新核对，不自动重发。另行确认的新消费不按金额去重 |
| 登录或加入中断 | 乙取消登录或返回后，成员列表里仍没有乙。只要邀请有效，乙再次打开可继续加入 |
| 重复接受 | 乙成功加入后重开同一卡片，若仍是成员，直接进入该账本。成员列表只有一个乙，原有角色保持当前值 |
| 撤销或过期 | 乙打开卡片后、确认加入前，甲撤销邀请，或邀请到期。乙提交时看到失效提示，仍可回到自己的账本；个人身份无法直接请求甲的流水 |
| 角色变化 | 乙先加入，甲再将乙改为只读。重开旧邀请时仍为只读；乙仍能看甲的午饭。甲移除乙后，乙刷新或使用旧卡片均无法读回甲的流水 |
| 数据归属 | 保存与读取都使用当前有效身份和目标账本。即使提交中带有其他记账人，系统也不得把甲的消费登记到乙名下。不同账本同名时按账本标识区分 |

## 如何验证

**本地联调。** 使用两个独立浏览器环境和独立登录会话，连接同一本地服务。微信身份和分享可用测试替身；账本、成员、流水必须由服务持久化。按上表操作，重启服务后重新读取，记录双方账本、流水标识、角色和金额，并记下保存结果不明时的提示。测试数据独立于日常原型数据。

**微信真机。** 使用两个真实微信账号、两台手机，从登录和分享卡片进入，复走主流程及邀请失效场景。双端刷新能读到同一条流水即可通过本次读取验收；即时推送另行考虑。

**当前证据。** 现有 H5 已在同一浏览器验证模拟登录、登记、标签页间接受邀请和改权限。独立会话的服务端联调与微信双机实测均待执行。
