# 小簿后端编码规范

这份约定用于小簿的 Java 业务模块。以支出录入为第一个可运行示例，不把示例里的预览身份当成正式鉴权方案。

## 分层与命名

Java 包按业务上下文组织，例如 `com.xiaobu.ledger`，再分 `interfaces`、`application`、`domain`、`infrastructure`。下表是**小簿工程约定**，不是 DDD 规定的类名后缀。先确定对象的业务含义，再加对应层的后缀。同一概念在代码、产品术语和文档中用同一个名字，不以表名倒推领域模型。

| 层 | 角色 | 命名规则 | 当前示例 |
| --- | --- | --- | --- |
| `interfaces` | HTTP 入口 | `<资源>Controller` | `ExpenseController` |
| `interfaces` | HTTP 输入、输出、转换 | `<动词><对象>Request`、`<对象>Response`、`<资源>WebMapper` | `RecordExpenseRequest`、`ExpenseResponse`、`ExpenseWebMapper` |
| `application` | 用例编排、事务与授权 | `<业务对象>ApplicationService` | `ExpenseApplicationService` |
| `application` | 写入参数、查询参数、用例结果 | `<动词><对象>Command`、`<动词><对象>Query`、`<对象>Result` | `RecordExpenseCommand`、`ListExpensesQuery`、`ExpenseResult` |
| `application` | 业务仓储接口 | `<聚合根>Repository`；接口不引用 Spring Data 或 JPA 实体 | `ExpenseRepository` |
| `domain` | 领域实体、聚合根、值对象 | 按业务名词，不机械追加 `Entity`、`Model`、`VO` | `Expense`、`ExpenseDetails` |
| `infrastructure` | 业务仓储实现 | `<聚合根>PersistenceAdapter`，实现对应的业务仓储接口 | `ExpensePersistenceAdapter` |
| `infrastructure` | 持久化实体和 Spring Data 接口 | `<持久化对象>Entity`、`<持久化对象>JpaRepository` | `LedgerTransactionEntity`、`LedgerTransactionJpaRepository` |
| `infrastructure` | 领域对象与持久化实体互转 | `<领域对象>PersistenceMapper` | `ExpensePersistenceMapper` |

### 仓储命名和术语边界

- `Expense` 是支出用例当前直接访问的领域对象，业务层使用 `ExpenseRepository`。实现是 `ExpensePersistenceAdapter`；**`PersistenceAdapter` 是业务仓储的实现类，`JpaRepository` 是 Spring Data 接口**。仅当需要隔离领域模型和持久化模型，或需要组合多个持久化操作时才加适配层；纯单表 CRUD 不为凑层数套一层。同一角色不另用 `Store`、`Dao` 或 `RepositoryImpl`。
- `LedgerTransaction` 是账本流水，`LedgerTransactionEntity` 映射收支共用表 `ledger_transactions`。因此 Spring Data 接口叫 `LedgerTransactionJpaRepository`，不用 `ExpenseJpaRepository`。只在基础设施包内使用它；`ExpensePersistenceAdapter` 负责对象转换、确定支出方向及拆分月份范围。
- 别按每张表给业务层建仓储。只有需要独立访问的业务聚合才设业务仓储；不能因为支出和收入共用一张表就合并领域模型。也不为了凑层数添加只转发的方法或预先拆读写仓储。
- 对照链路：`ExpenseController` → `ExpenseApplicationService` → `ExpenseRepository`（由 `ExpensePersistenceAdapter` 实现）→ `LedgerTransactionJpaRepository`。HTTP 对象、领域对象、持久化实体不跨层混用。跨层映射用 MapStruct，未映射的目标字段视为编译错误；业务判断不放进 Mapper。

### 方法与字段

- Controller 和应用服务对同一用例用同一个业务动词，如 `recordExpense`、`listExpenses`。避免只写 `handle`、`process`、`doSave` 这种看不出意图的名字。业务命令优先表达动作；例如记账用 `record`，不必模仿底层 `save`。
- 查询名反映语义：`list` 返回集合；`find` 允许找不到；`exists` 返回布尔值。仓储查询按业务条件命名，如 `findByLedgerAndMonth`；复杂 JPQL 用可读的名字，不把全部底层过滤和排序机械拼进方法名，也不能用模糊的名字或漏掉必要的账本范围。
- 映射方法用 `toCommand`、`toResponse`、`toDomain`、`toNewEntity` 这类能说明目标的名字。业务层不用 `save`、`deleteById` 等表级接口替代业务动作；Spring Data 接口保留框架方法名。
- Java 字段和 JSON 用 `lowerCamelCase`，数据库列用 `snake_case`；同一字段保留同一含义，例如 `bookedOn` / `booked_on`、`amountCents` / `amount_cents`。金额字段标清单位，业务日期和审计时间分开命名。

## JPA 与数据库

- Flyway 迁移脚本负责表、索引与约束；Hibernate 只做 `ddl-auto: validate`，不代替迁移。已运行过的迁移不原地改写。
- 单表增改查优先复用 Spring Data JPA 自带的 `save`、`findById` 和派生查询，不另外封装通用 CRUD，也不直接注入 `EntityManager` 做常规操作。账本流水用窄接口，只声明实际需要的方法，不暴露默认物理删除，也不能用裸 `findById` 代替带账本权限和逻辑删除条件的业务查询。
- 应用预先分配 ID 且实体没有版本字段时，用 `Persistable.isNew()` 显式标记新旧状态；加载和插入完成后切换为已存在。这样第一次调用 `save` 走 INSERT，不会因 ID 已有值而当作更新。修改流水时，先按业务范围查到已有实体，再修改；不能用请求数据重新构造一个新实体来更新。
- 简单查询优先派生方法；条件较多时用短命名加参数化 JPQL。过滤、排序和分页交给数据库；只有复杂报表、批处理或 MySQL 特性确有必要时才用原生 SQL，并记录理由、用目标版本验证。
- 业务日期用 `LocalDate` / `DATE`，审计时间按 UTC 写入；复用 Foundation 的时间戳回调，操作者由应用用例提供。流水保留 `created_by`、`updated_by` 和 `deleted`，列表明确过滤逻辑删除。不要把库中已有的 `deleted` 列自行替换为别的软删模型。
- 创建人是审计字段，不是共记权限。流水用例先按服务端会话中的操作者校验当前账本访问权限，再按账本读写。写入仍仅限账本所有者；读取允许所有者或已加入的只读成员。可记账角色另行实现。测试身份只能在绑定回环地址的本地 profile 中使用，不得用于生产。
- 金额以整数分保存；类型和状态按稳定编码落库，不用 Java 枚举序号。按最新决定不做统一防重组件，不加 `submit_key`；不得把客户端按钮锁当成服务端幂等保证。

## HTTP 与 XML

- HTTP 映射不重复声明默认请求体格式；只有需要明确区分媒体类型时才设置 `consumes`。
- Maven POM 和后端 XML 每级缩进两个空格，非空容器的开始、结束标签分行，依赖、插件和配置节点逐项展开。简单值和空元素可以独占一行。不要在格式化自身之外把改动扩散到未涉及的 Foundation 模块。

## 提交前验证

1. 新增或改名的类型，评审时按上表核对所在层、角色后缀及同一业务词是否一致；不同时引入同义命名。
2. 项目后端执行 `mvn -f backend/pom.xml verify`，通过格式、静态检查和单元测试。
3. 涉及 JPA、迁移或审计时间的变更，用与目标兼容的隔离 MySQL 重跑。仓库里的 `ExpensePersistenceMySqlTest` 仅在配置 `127.0.0.1` 上的 `xiaobu_expense_test` 时运行，检查金额、UTC 审计字段、账本/创建人隔离、收支方向、逻辑删除、月份起止日和主键冲突时不覆盖已有流水。不要连接线上库。
4. 从真实入口复核受影响流程；支出当前以 H5 交互和接口为准，微信小程序构建通过不能代替真机验收。
