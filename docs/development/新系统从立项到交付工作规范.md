# AI 辅助开发新系统工作规范

适用于从零建设、按版本交付的小型软件项目。以下阶段和模板是建议工作方式，可按项目风险裁剪。一人可以承担多个角色。复杂规则保留书面记录，简单项目可将多项产物合在同一份文档。

## 一位产品负责人如何与 AI 配合

产品负责人决定服务对象、目标、版本取舍、业务规则和发布时机；AI 在这些边界内负责整理需求、提出方案、实现、验证和交接。以下角色可以由同一人承担。按用户能完成的任务推进，每轮都留下可以复查的结果。

| 时点 | 负责人提供或决定 | AI 执行并留下的结果 |
| --- | --- | --- |
| 新项目启动 | 用户、问题、想达到的效果、使用环境与限制 | 一页项目简报，列出已知事实、待验证假设和判断成效的方法 |
| 定范围 | 确认模块边界、一期目标和优先级 | 建功能总表，为功能点分配稳定编号，将本期场景关联到模块说明和版本 PRD |
| 准备一项功能 | 决定影响用户权益、业务含义或版本范围的分歧 | 读取现有规范与实现，给出正常、异常和权限验收例子；对可逆的实现细节自行取舍 |
| 开发与验证 | 可随时用原型反馈交互 | 按一个可演示场景贯通页面、业务与存储，执行关联测试，从正常入口走流程，记录命令、环境、实际结果与未验证部分 |
| 验收与接续 | 在对应环境验收业务结果，决定优先级变化或是否发布 | 更新功能状态与交接记录。新会话读取相关资料，核对当前实现和运行方式，从尚未完成的一项继续 |

### 可复制的 AI 开发任务单

- 功能编号与用户结果：用户是谁，操作完成后能观察到什么。
- 依据与范围：引用已确认的模块规则、版本 PRD、原型入口和仓库约定。本轮涉及哪些端，哪些依赖仍在模拟。
- 验收例子：给定初始数据、执行操作、预期结果。写清至少一个影响正确性的异常场景。
- 执行边界：列出与本次任务相关的授权，例如仅本地开发。产品定义冲突时标记冲突和影响；能独立完成的部分继续推进。
- 交付记录：实现位置、运行方式、验证环境、实际观测结果、剩余问题和下一项。复用已有文档、任务或测试报告，链接到同一功能编号。

### 避免跨会话丢失决策

仓库约定保存长期有效的开发规则；模块说明保存业务规则；功能总表保存按端区分的状态；接力文档保存怎么运行和从哪里继续。每轮只改发生变化的那一处。用户调整业务规则时，在对应条目记下新决定，定位受影响的功能和验收例子，再调整实现。若测试失败，先核对已确认的预期；修改预期需要有对应的需求变化依据。

例如小簿的「成员修改本人流水」，可以先交付本地接口与双身份测试，再交付小程序页面及双机验收。同一条记录可以同时是“本地权限用例通过”和“小程序真机待测”。记录实测环境，新会话就知道该继续验证哪里。

## 工作流程

| 阶段 | 牵头人 | 主要工作与产物 | 阶段结束时回答 |
| --- | --- | --- | --- |
| 1. 问题发现与立项 | 产品负责人 | 访谈或观察目标用户，记录现有做法、痛点证据、替代方案、约束和成功指标，形成一页《项目简报》 | 为谁解决什么问题？改善多少才值得继续？ |
| 2. 业务梳理与范围 | 产品负责人和业务代表 | 梳理角色、业务对象、端到端场景及系统边界。建立《产品功能总表》，标明已知模块、功能点、优先级和计划版本 | 整体覆盖哪些业务？第一版要交付哪条完整用户流程？ |
| 3. 需求细化与原型验证 | 产品和设计 | 针对本期功能写《模块需求说明》，把权限、状态变化和异常写成可验收的规则。用原型验证难理解的交互和高风险假设，记录观察与修改 | 用户能否完成核心任务？业务方、开发和测试对结果的理解是否一致？ |
| 4. 技术设计与计划 | 技术负责人 | 明确系统边界、数据模型、接口契约、身份与权限、并发与失败处理、外部依赖。必要时做小规模技术验证。按用户场景拆迭代，标明负责人 | 最难的依赖如何验证？第一轮何时能演示什么？ |
| 5. 迭代开发与联调 | 开发负责人 | 每轮打通一条前端、服务端与数据贯通的流程。提交实现、自动化测试和可演示版本，记录已接入与仍模拟的依赖 | 从正常用户入口能否完成？刷新或重试后数据是否正确？ |
| 6. 测试与业务验收 | 测试与业务负责人 | 根据需求编写验收用例，覆盖正常、异常、权限和跨模块影响。在目标设备及适当数据规模下验证。记录结果、缺陷和遗留风险 | 哪些需求已经验收，证据在哪里？剩余风险由谁接受？ |
| 7. 发布与持续运营 | 发布与产品负责人 | 决定发布后，准备数据迁移、监控、备份恢复、回滚和责任人。发布后对照立项目标观察实际使用、故障与反馈；退役时安排数据迁出、留存和依赖下线 | 出问题如何发现和恢复？做出的系统有没有改善最初的问题？ |

阶段可以往返。原型暴露业务规则缺失时回到需求，技术验证暴露成本问题时重定版本范围。只在本地开发的项目可交付到本地验收，发布由项目负责人另行决定。

## 需求文档怎么组织

**产品功能总表**是所有已知功能点的索引。每行对应一个用户可辨认、可验收的行为。建议列为「编号、模块、功能点、目标角色、需求说明链接、优先级、目标版本、实现状态、验收证据」。多端产品分别记录各端状态，例如 H5 已演示、小程序待开发、双机验收通过。

**模块需求说明**记录该模块持续有效的业务规则。每个功能按需写明以下内容：

- 用户目的、发起角色、入口与前置条件。
- 正常步骤、字段与默认值、状态变化、成功后影响哪些数据与页面。
- 权限范围、空状态、取消、失败、重试和多人操作时的结果。
- 验收示例，写清初始条件、操作与可以观察到的结果。
- 原型页面、依赖、适用版本及待决策项。

**版本 PRD**从总表引用本期功能，说明版本目标、范围、优先顺序和跨模块验收场景。远期功能可以先留在总表中，排入开发计划时再细化。模块规则改动时更新原条目，版本记录说明改动原因、受影响模块和需重跑的用例。

## 一个可复用的验收例子

| 项目 | 示例 |
| --- | --- |
| 功能点 | 流水管理／修改本人流水 |
| 条件 | 乙是可记账成员，打开本人创建的 68 元支出 |
| 正常操作 | 乙改为 60 元并保存。双方刷新后均看到 60 元，支出合计减少 8 元，记账人仍为乙 |
| 异常操作 | 编辑期间管理员将乙改为只读。乙点击保存看到权限提示，双方看到的原始金额仍为 68 元 |
| 验收记录 | 同一功能编号关联端到端用例、实测环境、结果和版本。浏览器模拟与双机实测分别记录 |
