# 流水业务扩展与礼金接入

## 决策
- 一笔钱只写一条主流水。汇总、余额、退款仍读原有流水；礼单与亲友视图按同一个流水 ID 查，金额和日期不重复存。分类是统计维度，能力决定可附加的业务，不用显示名或客户端传入的能力清单判断。
- 后端用 Spring 注入按稳定 `type` 注册的 `TransactionExtensionHandler`。处理器声明其适用分类、是否必需，并负责自己的读写与领域校验。流水应用服务只做通用编排；不会为了礼金、租房、工资加三套条件分支。重复注册启动失败；未知、重复、不适用的能力由服务端拒绝。
- 新增和编辑在原记账事务内同步完成。写入失败全部回滚，不用事件或 MQ 保证核心一致性。异步通知、外部索引等未来副作用可以在提交后触发；需要持久重试时另行设计 Outbox。
- 每个业务自有强类型数据和表。可用的扩展类型通过分类目录返回；请求用 `extensions: [{type, operation, detail}]`，边界按模块声明的类型解码，JSON 不进入领域及持久层。纯读详情带相同类型标识。表单壳按能力挂载模块组件，仍只提交一次；服务端不下发组件名或表单脚本。

## 写入约束
- 新增：只接收 `UPSERT`，缺少必选能力拒绝。普通收支仍用原接口，无需传空扩展。编辑：省略类型表示保留；`REMOVE` 表示明确移除；`UPSERT` 提供完整的该业务明细。既有扩展不再适用的改类必须显式处理，不能随改类静默删除。
- 沿用账本写锁、成员权限及原流水版本。只改扩展也推进同一个版本。退款对方向、日期、金额的现有限制不变。删除、恢复整笔流水时扩展不级联删除；业务列表通过有效主流水控制是否可见。
- 礼金以 `GIFT_SENT`、`GIFT_RECEIVED` 区分方向；旧自定义分类单凭同名不迁移。命名冲突需可区分，不能把普通历史支出自动升级成往来。
- 礼金扩展先支持默认日常收礼／送礼，可无名、可无事由。正式礼单和亲友主数据各自独立，同名不自动合并。旧礼相记数据不连生产库，不自动同步；旧记录迁移、去重和对账单独验收。

## 交付切片与验收
1. 接通能力目录、通用编排、礼金默认礼单明细。验证基础 H5 收送礼录入、详情与编辑及普通收支不停摆、未知类型拒绝、第二个测试处理器不修改主流程；在隔离环境验证保存后同一流水、仅改附加字段也冲突保护、旧客户端省略保留、改类显式移除、失败回滚、删除恢复。
2. 按已确认 Vant 原型完成礼单和亲友选择与列表、同名处理、快速登记；从两个入口验证同一笔仅统计一次。未实现的目录不加假入口或按钮。真机测试另记，不把编译或浏览器点测当真机。
3. 后续租房/工资新增各自处理器、分类能力映射和 UI 组件，不复用礼金表，不要求一对一。工资权限不能直接等同于账本可读，列表摘要和备份均受各业务权限约束。
