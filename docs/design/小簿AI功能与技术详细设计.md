# 小簿 AI 功能与技术详细设计

2026-11-26 · 一期开发依据（设计稿，正式服务待实现）。适用于 uni-app 微信端、H5 联调端和 Java 服务。产品范围以[微信小程序一期 PRD](../product/微信小程序一期PRD.md)为准，功能编号沿用[产品功能总表](../product/产品功能总表.md)。

## 1. 用户能问到什么

用户可以用自己的说法查询有权查看的业务数据。同一组数据支持明细、筛选、合计、分组、比较和排序；团队按业务数据源接入一次，这些问法即可自由组合。例如“本月花了多少”“本月现金付的哪三笔最多”“上个月我登记的买菜支出按周合计”共用一套查询能力。新增问法的代价应该主要是补充语义评测；只有涉及新的数据来源、指标含义或计算方式，才需要补业务代码。

| 场景 | 一期行为 |
| --- | --- |
| 进入与返回（ASK-01） | 沿用底部中央入口与独立聊天页。顶部展示当前账本；点答案打开流水详情，返回保留会话位置，再返回保留流水页原筛选。游客只访问已有示例，查看私人数据走项目登录入口。 |
| 自由问账（ASK-03） | 在当前账本内查询已接入的收入、支出、退款及其明细，按日期、分类、账户或记账人组合筛选；支持按日、周、月或分类汇总及同期比较。可查当前账户、分类目录，账户当前余额使用已有余额口径。结果给出范围与来源。 |
| 连续追问（ASK-03、07） | “那上个月呢”继承上一问的分类和账户；“第二笔呢”指所选卡片里当时的第二笔。新建会话从空上下文开始；恢复历史只显示本人在该账本的会话。 |
| 对话记日常支出（ASK-04、05） | “昨天买菜”先追问金额，补“六十八块”生成可改、可放弃的草稿。用户确认后调用手工记账的同一写入用例；保存前两人的流水均无变化。 |
| 后续数据覆盖 | 现有礼金、活动礼单、亲友和转账明细可按数据源扩展。租房、固定账单、提醒等随正式业务落地接入。可读数据与可执行动作分别登记；收入或礼金的对话写入、退款确认卡（ASK-06）、语音（ASK-02）不作为一期交付条件。 |

**“我的数据”取决于对象的授权规则。** 个人账可看自己的账务数据；在共享账内，有读取权的成员可查本账本全部可见流水。“我记的”增加本人创建人条件，“我花的”若不能从已有字段判定，就问“看你登记的，还是整个账本的？”。对话、未确认草稿及个人偏好仅本人可见。一期一次查询绑定当前账本；问“我所有账本加起来呢”时说明当前范围并提供切换入口。跨账本合并统计另行定义授权和去重口径。

## 2. Skill、上下文和记忆怎样配合

这里的 Skill 是产品运行时的一项业务能力。提示词和工具契约放入 backend/src/main/resources/assistant/ 并随代码版本化；开发用 AGENTS.md 继续约束研发行为。运行时使用静态注册表。每项 Skill 声明名称、输入输出结构、所需读写权、是否产生草稿及允许返回的卡片。

| 组件 | 持有或处理的数据 | 产出 |
| --- | --- | --- |
| 上下文构建器 | 当前身份与账本已通过服务端校验。本轮原文、显式回复的卡片、当前任务、已确认查询条件，以及与问题相关的数据目录描述 | 提供给模型的最小上下文。业务 ID 和权限留在服务端 |
| 查询 Skill | 模型提出的查询计划、由服务端绑定的授权范围 | 校验计划并调用业务读模型；返回数字、明细引用或澄清选项。目录发现、解释一条流水也在此能力内完成 |
| 支出草稿 Skill | 金额原文、分类或账户称呼、当前草稿及版本 | 返回待补字段或草稿卡。对“改成 86”只更新选中的草稿 |
| 会话工作记忆 | 最近一次成功查询、来源卡引用、待澄清项、当前草稿引用、会话版本 | 帮下一轮确定该继承什么。落库后刷新可恢复；只有成功的任务转换才覆盖状态 |
| 历史与长期偏好 | 历史保存用户看到的消息。跨会话偏好另行设计为个人主动确认的别名或默认值 | 历史用于回看；长期偏好通过独立入口查看和忘记。一期只交付历史和会话工作记忆 |

**例：** 用户问“现金买菜花了多少”，服务端确定日期后，查询 Skill 解析账户和分类并查库，把条件及结果引用写入会话。随后“只看我记的”仅添加创建人条件。若点昨天的另一张卡再说“第二笔”，前端传该卡消息 ID，后端按其已展示的顺序解析。此时若说“帮我记买菜 68”，切入新草稿，旧查询的期间和账户不带入。若有两个可解释目标且用户未指明，先让用户选。

恢复上下文时按本轮明确指令、被引用的卡片或草稿、当前任务、产品默认值依次处理。超过模型输入预算时先舍去旧闲聊；保留完成本次操作所需的结构化条件。保留相对日期表达与当时解析的绝对日期：旧卡「查看明细」使用当时区间，新问“今天”按本轮北京时间重新计算。工作记忆可引用金额卡，询问“现在多少”仍重新查库。

## 3. 通用查询如何避免逐题开发

### 数据目录与领域口径

每个正式业务模块向查询目录提供**逻辑数据集**。目录登记数据粒度、可见角色、时间字段、显示字段、可筛选和分组的维度、允许的指标与运算、排序键、关联对象、明细入口。登记项同时包含用户术语与示例，如“买菜”对应当前账本分类候选。模型只看完成本题所需的业务描述，授权后的 Java 代码将逻辑名映射到受控的仓储条件。

| 数据集 | 粒度与授权 | 指标、维度及来源 |
| --- | --- | --- |
| 流水活动（一期） | 一笔有效流水或一笔到账退款；当前可读账本，排除已删除原单及其退款 | 收入、原支出、到账退款、净支出、结余、活动条数。日期、分类、账户、方向、记录人、备注。复用 LedgerStatementQueryRepository 的分页与日汇总语义；退款来源链接回原单。 |
| 账户、分类（一期） | 当前账本的一个目录项 | 名称、方向、启停状态及当前账户余额。账户金额沿用账户服务的期初、关联收支、退款和转账口径。余额为时点值，目录只开放适用操作；历史上的余额另需历史读模型。 |
| 礼金往来（扩展示例） | 一笔带礼金扩展的有效流水；复用礼金业务读权限 | 收礼、送礼金额及笔数，按礼单、亲友、方向和日期查询。复用 GiftActivityQueryRepository。亲友同名先选 ID；不能把普通备注自动当作礼金。 |

每个数据集一次只按一种粒度聚合。按亲友问礼金时从礼金活动出发，查原单使用已注册的业务关联；不把流水金额与礼金金额相加。含多笔退款的原单也不能因关联而重复累计。涉及两个指标时先核对口径；当前目录不支持可靠关联的请求，说明可查询的部分，提示可选的查询范围。后续模块上线时，交付清单应包含它的目录、授权、指标、来源链接和契约测试，逐步覆盖所有可见业务数据。

### 模型输出与执行

以“这个月我记的现金支出按分类排前三”为例，模型输出的逻辑计划如下。关键词、同义表达和句子顺序可变化；同类查询均走这一协议。

```json
{
  "dataset": "statement",
  "operation": "aggregate",
  "period": "THIS_MONTH_TO_DATE",
  "filters": [
    {"field": "account", "op": "eq", "text": "现金"},
    {"field": "recorder", "op": "eq", "value": "SELF"}
  ],
  "metrics": ["netExpenseCents"],
  "groupBy": ["category"],
  "orderBy": [{"field": "netExpenseCents", "direction": "desc"}],
  "limit": 3
}
```

1. 根据会话和成员关系生成可见目录。选用 DeepSeek 理解中文，允许返回查询、澄清、草稿或当前不支持；Spring AI 为拟用模型适配层，先在本仓 Foundation BOM、Boot 与 JDK 27 下验证依赖。供应商调用隔离在出站接口后，技能契约、权限、会话和草稿留在小簿。沿用[基础能力归属](双人共记一期技术方案与迭代计划.md)。
2. 服务端验证协议版本、字段类型、运算和指标组合。SELF 从会话绑定；“现金”在本账本解析，多个候选给出澄清卡。相对日期用可注入的 Clock 和 Asia/Shanghai 展开。只有执行器可指定账本范围、字段映射及固定关联；忽略文字中的身份声明，拒绝目录外字段及表达式。
3. 领域查询层把规范化计划编译成参数化查询。列表、汇总和钻取共享相同筛选条件；分组、排序和分页在数据库执行。同值排行以稳定分类键打破并列，明细复用现有日期、类型、创建时间和 ID 排序。沿用 MySQL 5.7；单次日期范围最多 366 天，明细每页默认 20、上限 100。超范围请用户缩小。比较限定两个明确区间，执行设置超时，在目标数据量上检查查询计划。
4. 每个结果给出账本名、时间区间、有效筛选、统计口径、数据时间及来源。空集返回“没有匹配流水”；完全退款返回“净支出为零”及构成；执行失败返回可重试状态，不把失败显示为零。敏感字段、未接入模块、超出权限及无法判断的问题均不生成臆测值。对无权限对象的响应不透露其是否存在。
5. “比上月呢”继承可见条件，月中默认同期，短月取月末；明确问“上月整月”时按整月。卡片始终展示两段实际日期，上期为零时显示差额。结果引用保存条件、展示顺序和计算时点；钻取时重新鉴权并读取最新结果。账本已变化则展示最新合计及变化提示，历史卡保留原回答时间。

**扩展验证。** 在已有流水数据集登记“记账人”维度后，“我记的餐饮有几笔”“各记账人支出排行”应通过同一规划协议和查询入口得到答案。接入礼金则新增数据集及领域适配，沿用相同筛选、分组和排行运算。新增独有指标（例如应收未收房租）须由相应业务定义和实测后才开放。模型提出任意新问法，不等于任意数据库表或字段自动开放。

## 4. 会话、接口与一致性

Java 单体的 assistant 包按 interfaces、application、domain、infrastructure 分层。前端从已确认原型复用聊天交互，支持文字、结果卡、澄清选项、草稿卡及来源详情，查询结果由服务端精确值渲染。建议的接口及归属如下。

| 操作 | 方法与路径（统一前缀 /api/v1） | 服务端校验与结果 |
| --- | --- | --- |
| 新建、列历史 | POST / GET /ledgers/{ledgerId}/assistant/conversations | 检查读取权限，历史仅按当前用户和账本分页 |
| 发送、恢复消息 | POST / GET /assistant/conversations/{id}/messages | 校验会话归属与成员资格。发送接收文字或候选引用，可带 replyToMessageId，返回任务状态和类型化卡片 |
| 钻取明细 | GET /assistant/messages/{id}/entries | 校验归属、可见范围与分页，按该卡的条件或分组键列出参与计算的活动 |
| 修改、放弃草稿 | PATCH /assistant/drafts/{id} | 校验所属会话、目标账本与草稿版本，失配返回最新版本供核对 |
| 用户确认保存 | POST /assistant/drafts/{id}/confirm | 校验写权限及版本，重验账本内分类和账户，复用现有日常支出写入服务 |
| 恢复保存状态 | GET /assistant/drafts/{id} | 在当前权限内返回最终状态与已关联流水，支持回包丢失后先核对 |

建议三张 MySQL 表：conversations 保存 owner、ledger、上下文及版本；messages 保存会话、发送者角色、请求标识、正文、卡片和协议版本，按会话与顺序分页；drafts 保存会话、原账本、规范化字段、版本、状态及已保存的流水 ID。归属、外键、索引和状态单列；卡片和可演进的上下文用版本化 JSON。历史保留期限和删除策略在启用真实用户历史前明确；长期偏好后续独立存储、确认、查看及删除。成员离开时其原流水与署名沿用现有规则。

消息处理使用短事务登记，释放连接后调用模型，返回时重验成员权限与会话版本，再保存结果。同会话已有请求在途时提示等待并保留输入；服务重启后超时任务允许核对并重试。切换账本时清屏、取消旧请求展示；访问历史、来源或草稿均须重新鉴权。模型只取得本轮必要文字和目录描述，真实凭证、成员表和整本账不进入提示词。首次使用真实 AI 说明用户输入的发送范围。日志用英文记录请求编号、耗时、版本及错误类别，业务异常向用户返回中文；评测使用合成数据。

草稿按“待补全 → 待确认 → 已保存／已放弃”流转。中文金额精确到分；日期、分类、金额必填，账户可空。缺字段只追问相应项；查账条件不自动成为新草稿默认值。切换账本后草稿仍归原账本，用户要改目标须重新发起。确认时按项目统一的锁顺序校验角色、草稿版本及状态，在同一事务写主流水和已保存引用；失败一起回滚。结果不明时保留草稿、先查状态，不自动重发；本设计不增加通用提交键或全局防重组件。

## 5. 一期开发顺序与验收

步骤 1 的授权查询目录、组合筛选和六种数据库分组已在本地隔离 MySQL 验证；步骤 2 的只读对话已在 H5 与隔离服务验证，真实模型与微信双机仍待验收。步骤 3 至 5 待完成。先完成项目约定的双人共记联调前置，再接正式助手。每项有独立出口，记录代码版本、数据夹具、环境和实际结果。底部入口、确认卡和返回行为对照[既有原型](../ui-design/vant-pilot/src/AskPage.vue)。

| 步骤 | 开发交付 | 可观察的完成条件与环境 |
| --- | --- | --- |
| 1 · 数据目录和计算口径 | 从流水分页、账户和分类服务整理字段、粒度、权限及来源；实现通用查询计划、校验、执行和钻取 | 隔离 MySQL 5.7：同一条件下列表、汇总、排行、来源记录对齐；超过一页、上一月原付本月退款、同值排行、无记录、全退分别验证。换问法无需新 Controller。 |
| 2 · 只读对话与追问 | 新建／历史、消息卡、上下文、模型适配、中文分类与账户消歧；从正常入口进入并返回 | 本地 H5＋隔离 Java 服务＋模拟模型：走“本月餐饮 → 只看现金 → 看第二笔”，验证条件继承、来源 ID、会话恢复及原流水页筛选。固定时钟复测跨月；切换个人／共享账、跨成员访问旧卡和模型响应期间撤权均验证。 |
| 3 · 支出草稿 | 追问、修改、放弃、确认、状态恢复；接现有保存用例 | 两个独立登录会话：甲有 32 元午饭，乙输入“昨天买菜”再回复“六十八块”。确认前只有 32 元，确认后两端均为 100 元且署名乙。放弃、降权、旧版本、回包丢失分别验收；旧草稿不能写入新账本。 |
| 4 · 泛化与真实模型验收 | 锁定模型配置、提示词和目录版本；建立合成中文题集，将开发例句与留出题分开 | 在允许的真实 DeepSeek 测试环境跑留出题，记录意图、规范化计划、澄清及最终答案。固定样例的金额、归属和来源必须完全正确；权限用例全部通过。未见组合需由同一执行器正确执行或就真实歧义澄清；超出目录要说明缺项。模拟与真实模型分别出结果。 |
| 5 · 微信双机验收 | 编译微信端，串起真实登录、共享账问答、草稿及历史 | 按[双机清单](../specs/微信双机验收清单.md)及一期 PRD，用两个微信身份、两台手机复测步骤 2、3；弱网时能核对保存结果，移除成员后旧会话与明细均不可读。缺少环境记为待测。 |

### 固定验收样例

在同一共享账准备三条普通流水：11 月甲现金餐饮 32 元、乙现金买菜 68 元、乙工资收入 100 元。另有 10 月甲现金餐饮支出 50 元，其 8 元退款于 11 月到账现金。个人账另放一笔 999 元餐饮。在北京时间 11 月 26 日查询以下问题：

| 输入 | 应答或动作 |
| --- | --- |
| “这月支出多少，钱花哪了？” | 原支出 100、退款 8、净支出 92；按分类为买菜 68、餐饮 24。按净支出降序。净支出来源为两笔支出加一笔退款；工资不进入这张支出卡。 |
| “本月收支结余呢？” | 收入 100、净支出 92、结余 8。个人账的 999 元不参与共享账任何计算。 |
| 乙问“我登记的现金买菜，11 月有几笔？最大的那笔呢？” | 一笔、68 元；可打开乙所记原单。将同一问题换成“挑出这个月我用现金登记的最高一笔菜钱”，在类目能唯一解析时返回同一 ID。 |
